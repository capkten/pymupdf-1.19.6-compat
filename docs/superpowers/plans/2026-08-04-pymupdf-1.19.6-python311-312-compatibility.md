# PyMuPDF 1.19.6 Python 3.11/3.12 适配实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在保持 PyMuPDF 1.19.6、MuPDF 1.19.x 和既有 PDF 输出基线不变的前提下，验证并尝试构建 Python 3.11、3.12 的 Windows wheel。

**Architecture:** 先在当前源码上建立可重复的基线，再创建一个私有 GitHub 仓库或私有 fork 保存 CI 配置和构建产物。CI 固定 MuPDF 源码、SWIG、MSVC、Python 版本和测试样本；只在 C 扩展编译失败或回归测试失败时修改兼容层，不修改 PDF 处理逻辑。Python 3.10 作为对照组，Python 3.11/3.12 作为实验组。

**Tech Stack:** Python 3.10/3.11/3.12, setuptools, SWIG, C/C++, MuPDF 1.19.x, GitHub Actions Windows runners, pytest, wheel, hash verification.

## Global Constraints

- PyMuPDF binding version remains `1.19.6`.
- MuPDF native source/library must remain the same 1.19.x line used by this binding; do not silently use a newer MuPDF.
- Python 3.10 is the output baseline; 3.11 and 3.12 must be compared against it using identical input PDFs.
- No public repository is required; a private GitHub repository or private fork is sufficient for CI and artifacts.
- Every generated wheel must record Python version, OS architecture, compiler, SWIG version, MuPDF revision, and SHA-256 hash.
- The existing `setup.py` metadata mismatch (`1.19.5`) must be corrected to `1.19.6` before publishing any rebuilt wheel.

## 是否需要创建 GitHub 仓库

不属于技术上的硬性要求，但本项目建议创建一个私有仓库或私有 fork，名称可以是 `pymupdf-1.19.6-compat`。原因是当前目录没有 Git 仓库、没有 CI 配置，而且适配需要保存构建脚本、版本锁定文件、失败日志和 wheel artifacts。

建议分两步：先在本地 Python 3.10 上完成基线和构建输入确认，再创建私有 GitHub 仓库启用 Windows CI。这样不会把尚未验证的兼容构建发布到公共 PyPI，也不会修改原始 PyMuPDF 项目的历史版本。

## 完成标准

- Python 3.10/3.11/3.12 均能在同一套固定 MuPDF/SWIG 输入下生成对应 wheel，或明确记录具体失败原因。
- `import fitz`、完整测试和黄金样本测试通过。
- Python 3.11/3.12 与 Python 3.10 的稳定输出一致。
- wheel、构建环境、依赖版本和 SHA-256 可追溯。
- 未通过验证的 Python 版本不会被声明为生产支持版本。
